# QA 가상 데이터 납품 및 검증 보고서

- 생성 실행일: 2026-10-14 / 데이터 기준일: **2026-09-30**
- 대상 기간: **2026-01-01~2026-09-30**
- 데이터셋 ID: `QA26JANSEP_V1` / 식별 접두: `[가상 QA26JANSEP_V1]`
- 납품 상태: **기존 장부 백업 후 활성 장부 교체 완료**, 앱 조회 API 재확인 완료
- 입력 방식: 브라우저 수동 입력이 아닌 **MVP의 POST API 처리기**를 통한 입력. 격리 장부에 먼저 입력하고 검증 후 활성 원본 경로에 설치했다. 앱 코드는 수정하지 않았다.
- 오류·경고 데이터는 파일로만 생성했으며 제출하지 않았다. QA 체크리스트의 미실행 상태는 변경하지 않았다.

## 1. 적용 구조와 규칙

재원코드와 과제명은 재원 레코드의 서로 다른 필드다. 예산은 재원·예산목·변경회차별 이력이며 집행·품의와 별도다. 인원·인건비지급·적립금·신청·주문은 각각 독립 엔터티이고 앱의 동작 API로 연결했다.

근거: [사용 안내](../../app/README.md), [저장·검증 로직](../../app/store.py), [서버](../../app/main.py), [QA 체크리스트](../QA_기본체크리스트_2026-10-14.md). 필드·자료형·식별열·선택값 목록은 [schema.json](schema.json)에 수록했다.

| 엔터티 | 주요 필수값·자료형 | 고유·연결 규칙 |
|---|---|---|
| 재원 | 재원코드 문자열 필수; 과제명·기간 선택 | 코드 고유, 하이픈 금지; QA01~QA10 |
| 예산변동 | 재원·변경회차 필수, 예산목별 숫자 | 같은 재원에 이월·당초·숫자회차 중복 금지 |
| 집행 | 재원·예산목·원인발생일·0 아닌 금액 | 거래번호 자동; 선택값 공란 허용; 단계는 날짜에서 계산 |
| 품의 | 집행 공통 필수값, 상태 | 대기만 전환 가능; 전환 저장 시 집행 생성·집행완료 |
| 적립금 | 일자·거래처·적립/사용·양수 금액 | 적립의 집행기록 옵션 사용 시 연결거래번호 생성 |
| 인건비 | 등록 인원·지급처·지급월·양수 금액 | 예정으로 추가 후 확정 동작; 지급월·귀속월·이름·지급처 조합 중복 제한 |
| 신청 | 구분·신청인·품목; 날짜 명시; 비학회 단가양수·수량양의정수 | 신청번호 자동. 소모품 구매처 및 상품/온라인코드 필요 |
| 주문 | 승인된 소모품 신청 묶음 | 같은 구매처만; 주문일≥결재일, 배송일≥주문일 |

날짜는 ISO `YYYY-MM-DD`, 월은 `YYYY-MM`, 금액은 원 단위 숫자로 생성했다. 예산현액=이월+당초+변경, 집행액=미완료 포함 모든 집행 금액, 잔액=예산현액−집행, 가용잔액=잔액−대기품의다. 월 필터는 집행 조회에 적용하고 잔액은 파일 전체 기준이다.

범용 CSV/XLSX 가져오기 UI는 확인하지 못했다. JSON 파일은 검토·재현 자료이며 **그대로 UI에서 가져올 수 있는 파일이라고 주장하지 않는다**. `synthetic_baseline.xlsx`는 앱 원본 DB 형식의 복원용 파일이다.

### 가정 및 확인 필요

- 기간은 1~9월로 고정하고 모든 업무 날짜를 명시했다. 자동번호·백업 파일의 시스템 생성 시각은 실제 실행일과 다를 수 있다.
- 가상 예산 규모·지급액은 QA 분포를 위한 값이며 실제 기관의 집행·급여 기준이 아니다. 가상결재자의 처리 기록은 Alex의 실제 승인권한을 뜻하지 않는다.
- 현재 소스는 집행을 발생→청구→보완→완료(지출완료일)→결의(결의일)로 표시한다. README·기존 QA 문서의 승인→완료 명칭과 다르므로 상태명 합격 기준 확정이 필요하다.
- 음수·초과는 경고 검증으로, 기간 밖·미등록 재원은 정책 확인용으로 분리했다. 정상 장부에는 넣지 않았다.
- 고액 신청 경계값은 검증 상한 사례다. 신청 상태로만 저장하여 예산 집계에 반영되지 않는다.
- 문서의 MB 한도와 소스의 1024 기반 용량 정의 차이는 첨부 QA 때 확인한다.
- 일반 집행의 미등록 재원 서버 차단은 확인되지 않았다. 잘못된 참조의 확정 거부 사례에는 등록되지 않은 인원을 쓰는 인건비를 사용했다.
- 공급처가 전부 가상이 되도록 설정의 구매처 목록에 `가상문구A`, `가상문구B`를 추가했다. 기존 목록과 나머지 설정은 보존했다. 이미 실행 중인 프로세스는 재시작해야 설정을 다시 읽는다.

## 6. 사용·재사용·복원

1. 앱·MCP·엑셀을 종료한 상태에서 사용할 장부를 선택한다. 실행 중이었다면 이번 교체 후 앱을 재시작한다.
2. `app/run.bat`으로 실행하고 재원 QA01~QA10을 확인한다. 실제 브라우저 확인은 사용자가 수행하거나 연결된 브라우저 환경에서 후속 QA로 수행한다.
3. 초기 가상 상태로 되돌리려면 현재 테스트 장부를 별도 복사한 후, 이 폴더의 `synthetic_baseline.xlsx`를 위 활성 장부 경로에 복사하여 교체한다. 신규 레코드를 덧붙여 재생성하지 않는다.
4. 실제 기존 데이터로 복원하려면 위 기존 장부 백업을 활성 장부 경로에 복사하고, 필요하면 `original.env`를 `app/.env`로 복원한다. 이후 앱을 재시작한다. 기존 설정 백업 후 별도 설정 변경이 있었다면 전체 덮어쓰기 대신 구매처 설정만 검토하여 복원한다.
5. 정리 기준은 데이터셋 접두 `[가상 QA26JANSEP_V1]`, 재원 QA01~QA10, 가상 인원·거래처, 식별자 목록이다. 최소 필수값 사례와 자동생성 연결행에는 접두가 없는 경우가 있으므로 접두 검색만으로 삭제하지 않는다. 전체 baseline 복원이 가장 재현성이 높다.
6. 오류·경고 JSON은 자동 입력 로그에 포함되어 있지 않다. 별도 QA 실행 시 각 사례를 하나씩 제출하고, 다른 오류가 섞이지 않도록 baseline과 지정된 사전조건을 복원한다.

설치 도구는 설치 완료 표시가 있으면 중복 입력을 하지 않으며, 활성 장부가 그 뒤 변경되었으면 덮어쓰기를 거부한다. 기존 장부 해시·앱 코드 해시가 준비 단계와 다르면 설치하지 않는다.

### 모의 드라이브 주의

- 증빙·첨부 파일은 이 폴더의 `qa_drive_mock/`(git 제외)에 있다. 장부의 드라이브파일ID는 `mock:증빙관리/…`·`mock:신청/…` 형태의 루트 기준 상대 경로이고, 증빙폴더·첨부폴더 열에는 실행 PC의 절대 `file:///` 경로가 들어 있다.
- `app/run_qa.bat`의 모의 드라이브 루트는 코드상 `app/drive_mock/`(drive.py `MOCK_DIR`, 환경변수로 바꿀 수 없음)이다. QA 서버에서 미리보기·파일 열기를 확인하려면 `qa_drive_mock/`의 `증빙관리`·`신청` 폴더를 `app/drive_mock/`로 복사해야 한다. 복사하지 않으면 장부 기록·증빙번호·결의서 목록은 정상이고 미리보기만 비어 보인다.
- V1 상태(보완 전, SHA-256 `8fabdc86…`)는 `synthetic_baseline_v1.xlsx`로 남겼다(xlsx는 git 제외). `qa_drive_mock/`이 없는 PC에서는 이 V1 파일을 `qa_ledger.xlsx`로 복사한 뒤 `supplement_v11.py`를 다시 실행하면 같은 레코드와 같은 파일(바이트 동일, 업로드일만 실행일)이 생성된다. V1.1 상태 복원은 `synthetic_baseline.xlsx` 복사로 한다.
