# 권한(역할) 설계 — 2026-10-20

> 2026-10-20 갱신: 이 문서가 쓰일 때는 사용자 파일이 `app/users.json`이었다. 그 뒤 구글 로그인(950dca2)과 SQLite 이전으로 저장 위치가 바뀌었다: 마스터는 `app/.env`의 `LEDGER_ALLOWED_EMAILS`, 나머지 계정은 SQLite `users` 표(이메일·이름·역할·허용). 설정 화면의 "로그인 허용 계정" 묶음에서 마스터가 관리한다. 6절의 JSON 형식과 5.3절의 무로그인 모드는 더 이상 맞지 않는다. 역할 4개와 4절의 권한 매트릭스는 그대로다.

구현은 나중에 한다. 이 문서는 역할, 행동별 권한, 로그인 방식, 저장 형식, 구현 순서를 정한다.

## 1. 배경과 문제

- 지금 앱은 로그인이 없다. 담당자/연구원 구분은 화면 표시뿐이고 API(`/api/…`)는 누구나 같은 동작을 부를 수 있다(README 4절, PRODUCT.md).
- 서버는 127.0.0.1에만 열려 있어 지금은 문제가 없다. 연구원이 다른 PC에서 신청 화면을 쓰려면 서버를 네트워크에 열어야 하고(LEDGER_HOST 과제), 그 순간 서버가 "누가 무엇을 할 수 있는지"를 검사해야 한다.
- 2026-10-16 학회 탭 점검 D8에서 서버 역할 검사를 보류했다(ideas.md). 이 문서가 그 설계다.

## 2. 역할 (2026-10-20 결정)

| 역할 | 누구 | 앱에서 하는 일 |
|---|---|---|
| 마스터 | 앱 운영자 | 사용자·역할 관리, 설정(구글 드라이브·AI·발주서), 담당자 권한 전부 |
| 관리자 | 센터장·실무교수·선임연구원·매니저 | 열람 전부 + 결재(신청 승인/반려) |
| 담당자 | 연구비 회계 담당자 | 장부 입력·수정(집행·품의·예산변동·적립금·인건비), 신청 처리, 주문, 증빙, 전결 |
| 연구원 | 센터 연구원 | 신청 입력, 본인 신청 확인·수정·삭제(신청 상태), 첨부 |

역할은 직책이 아니라 "앱 안의 행동"으로 가른다. 관리자 네 직책은 앱 안에서 같은 일을 하므로 역할 하나로 둔다. 직책은 사용자 파일의 표시용 필드로만 남긴다.

역할은 포함 관계다: 마스터 ⊃ 담당자. 관리자는 담당자와 겹치지 않는다(관리자는 입력하지 않는다). 연구원은 가장 좁다.

## 3. 결재 방식

- **단독 결재**: 관리자 중 누구든 한 명이 승인하면 승인이다. 순차 결재(담당 → 매니저 → 선임연구원 → 센터장)는 "나중"이다.
- **담당자 전결**: 담당자(마스터 포함)도 승인·반려할 수 있다. 구두 허가를 받은 건만 올라오므로 결재권자가 직접 누를 필요가 없다.
- **기록**: 신청의 `결재인`에 로그인 사용자의 표시 이름을 쓴다. 담당자가 승인한 건은 `결재인`에 "이름 (전결)"로 적는다. 열 추가 없이 기존 열을 쓴다. 관리자가 직접 승인한 건은 이름만 쓴다.
- **결의서 결재란**: 인쇄 모양은 바꾸지 않는다(담당·매니저·선임연구원·센터장 4칸, 빈 칸, 손 서명). 앱의 승인은 결의서 서명을 대신하지 않는다.
- 승인 취소·재신청도 결재 행동이다(관리자·담당자).

## 4. 행동별 권한 매트릭스

○ = 가능, △ = 조건부, × = 불가. "담당자"는 마스터를 포함한다.

### 4.1 화면

| 화면 | 관리자 | 담당자 | 연구원 |
|---|---|---|---|
| `/` 회계대장(집행·품의·예산·적립금·보고서) | ○ 열람만 | ○ | × |
| `/labor` 인건비 | ○ 열람만 | ○ | × |
| `/request` 신청 | ○ 열람 + 결재 | ○ 담당자 모드 | ○ 연구원 모드 |
| 설정(톱니) | × | △ 마스터만 (신청·발주서 설정은 담당자도) | × |
| 헤더 AI 버튼 | × | ○ | × |

관리자가 `/`·`/labor`를 열면 입력·수정·삭제 버튼과 행 편집이 숨겨진다(읽기 전용 모드). 별도 읽기 전용 화면(대시보드)은 "나중"이다.

규칙:
- 거부는 401(로그인 없음) 또는 403(역할 부족)으로 답한다. 화면은 403을 "권한이 없습니다. 담당자에게 문의하세요."로 보여 준다.
- 연구원의 "본인 건"은 신청의 `신청인`이 로그인 사용자의 표시 이름과 같은 건이다. 연구원이 신청을 추가하면 서버가 `신청인`을 로그인 이름으로 덮어쓴다(폼 값 무시).
- 지금 `extra.admin`, `extra.keep_approval`은 화면이 보내는 표시다. 구현 때 서버가 역할로 판단하고 이 값들은 무시한다.
- 같은 역할 안에서는 사람을 구분하지 않는다(담당자 A가 만든 행을 담당자 B가 고칠 수 있다).

### 4.3 연구원에게 보이는 데이터

`GET /api/all`은 지금 장부 전체를 돌려준다. 연구원 모드에서는 서버가 응답을 줄인다:
- `request` 시트 전체(다른 연구원 건도 목록에 보인다. 지금 연구원 화면과 같다). 단, 다른 사람 건은 수정·삭제·첨부가 막힌다.
- `suppliers`, `supplier_note`, 재원 목록(관련과제 선택용: 재원명·코드만, 금액 없음).
- 집행·품의·예산·적립금·인건비·증빙은 보내지 않는다.

관리자는 전체를 받는다.

## 5. 신원 확인: 구글 로그인

전원이 개인 Gmail로 로그인한다(2026-10-20 결정). 병원 계정은 쓰지 않는다.

### 5.1 흐름

1. 로그인하지 않은 브라우저가 어떤 화면이든 열면 `/login`으로 보낸다. `/login`에 [Google로 로그인] 버튼 하나.
2. 버튼 → 구글 OAuth 동의 화면 (scope: `openid email profile`만. 드라이브 권한은 요청하지 않는다).
3. 구글이 `/auth/callback`으로 돌아오면 서버가 ID 토큰을 검증하고 이메일을 얻는다.
4. 이메일이 `app/users.json`에 있으면 세션을 만들고 역할을 붙인다. 없으면 "등록되지 않은 계정입니다. 마스터에게 등록을 요청하세요."를 보여 주고 세션을 만들지 않는다.
5. 세션은 서버 메모리 + 서명된 쿠키(HttpOnly, SameSite=Lax). 만료 12시간. `/logout`으로 지운다.
6. 모든 `/api/…`는 요청 시작에서 세션 → 역할을 읽고 4.2 표로 검사한다. FastAPI dependency 하나로 묶는다.

### 5.2 구글 클라이언트 — 확인 필요 (구현 0단계)

지금 드라이브 연동의 `app/google_client_secret.json`은 **데스크톱 앱** 클라이언트다. 웹 로그인에는 **웹 애플리케이션** 클라이언트와 승인된 리디렉션 URI가 필요하다. 구글은 리디렉션 URI에 HTTPS를 요구하고(localhost 예외) 사설 IP 주소는 허용하지 않는다. 그래서 `http://192.168.x.x:8791`로는 로그인이 안 된다.

구현 전에 하나를 고른다:
- (a) **Tailscale**: 각 PC에 설치, 서버에 `https://<이름>.ts.net` 주소와 인증서가 생긴다. 무료, 병원 망 설정 불필요. 추천.
- (b) 병원 내부 DNS 이름 + 자체 인증서: 구글이 그 도메인을 받아 주는지 확인해야 한다.
- (c) 구글 로그인 대신 마스터가 발급하는 초대 링크(토큰): 구글 정책과 무관하지만 2026-10-20 결정과 다르므로 (a)·(b)가 모두 막힐 때만.

같은 구글 클라우드 프로젝트에 웹 클라이언트를 하나 더 만들면 된다. 드라이브 토큰(`google_token.json`)은 그대로 쓴다.

### 5.3 무로그인 로컬 모드

다음 두 조건이 모두 맞으면 로그인 없이 지금처럼 동작하고 모든 요청을 마스터로 본다:
- `app/users.json`이 없다, 그리고
- 서버가 127.0.0.1에만 열려 있다(`LEDGER_HOST` 없음).

둘 중 하나라도 아니면 로그인이 필수다. `users.json`이 있는데 `LEDGER_HOST`가 없으면 로컬에서도 로그인한다(설정 시험용). `LEDGER_HOST`가 있는데 `users.json`이 없으면 서버가 시작하지 않고 이유를 적는다.

MCP 서버(`mcp_server.py`)는 로컬 프로세스이고 장부 파일을 직접 읽으므로 역할 검사 밖이다. 마스터와 같다.

## 6. 사용자 파일 `app/users.json`

```json
{
  "users": [
    {"email": "a@gmail.com", "name": "박○○", "role": "master", "title": "담당자", "active": true},
    {"email": "b@gmail.com", "name": "김○○", "role": "manager", "title": "센터장", "active": true},
    {"email": "c@gmail.com", "name": "이○○", "role": "staff", "title": "", "active": true},
    {"email": "d@gmail.com", "name": "최○○", "role": "researcher", "title": "", "active": false}
  ]
}
```

- `role`: `master` / `manager`(관리자) / `staff`(담당자) / `researcher`(연구원). 코드와 문서에서 이 네 단어만 쓴다.
- `name`: 장부의 `신청인`·`결재인`과 맞추는 표시 이름. 기존 신청의 `신청인`과 같아야 본인 건으로 잡힌다(2026-10-19에 신청인 이름을 통일해 두었다).
- `title`: 직책, 표시용. 권한에 쓰지 않는다.
- `active: false`는 로그인 거부. 삭제 대신 쓴다(기록의 이름을 남긴다).
- 비밀번호가 없으므로 해시도 없다. 파일은 gitignore하고 `.env`와 같은 등급으로 다룬다(이메일 목록).
- 마스터가 0명이면 서버가 시작하지 않는다.
- 장부 xlsx에는 사용자 정보를 넣지 않는다.

## 7. 화면 변경 (구현 때)

- 헤더 오른쪽에 로그인 이름·역할·[로그아웃]. 지금 탭 막대의 "담당자" 표시(브라우저 탭 세션)는 없애고 역할로 대신한다.
- `/request` 모드는 주소가 아니라 역할로 정한다. 연구원은 담당자 모드로 들어갈 수 없다.
- 관리자: 회계대장·인건비는 읽기 전용(버튼 숨김 + 서버 403). 신청 화면에는 결재 버튼([승인] [반려] [승인 취소] [재신청])만, 품의 전환·주문·삭제는 없다.
- 담당자 승인 버튼 옆에 "전결" 표시. 상세 패널의 결재 정보에 "결재인: 이름 (전결)".
- 설정 화면에 **사용자** 탭(마스터만): 이메일·이름·역할·직책·활성 목록, 추가·수정. 이 탭은 "나중" 목록에 있다. 1차 구현은 파일을 손으로 편집한다.

## 8. 구현 순서 (각 단계가 혼자 커밋 가능)

0. 구글 웹 클라이언트와 HTTPS 주소 확보(5.2). 여기서 막히면 (c)로 결정하고 이 문서를 고친다.
1. `users.json` 읽기 + 역할 상수 + 무로그인 로컬 모드 판정. 테스트: 파일 없음/있음, 마스터 0명.
2. `/login`, `/auth/callback`, `/logout`, 세션 쿠키. 테스트는 구글을 부르지 않고 ID 토큰 검증 함수를 가짜로 바꿔 돌린다(`LEDGER_AUTH_MOCK=1`, 드라이브 모의와 같은 방식).
3. API 검사 dependency + 4.2 표 적용. 테스트: 역할 4개 × 대표 경로마다 200/403. 기존 `extra.admin` 제거.
4. 연구원용 `/api/all` 축소(4.3) + 본인 건 검사.
5. 화면: 헤더 로그인 표시, 역할별 버튼 숨김, 관리자 읽기 전용, 전결 표시.
6. `LEDGER_HOST`로 네트워크 공개 + README 갱신. QA 장부로 다른 PC에서 시험.

각 단계 뒤 `scripts/check.sh`. 기존 UI 테스트(Playwright)는 무로그인 로컬 모드로 그대로 돌고, 역할 테스트는 `users.json`을 `tests/.tmp/`에 만들어 돈다.
